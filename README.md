# UZMARKET GAMING

Локальный прототип игрового маркетплейса для Узбекистана (по мотивам FunPay): покупатели, продавцы и администратор, который зарабатывает комиссию.
**Основатель и руководитель проекта — Saidakbar.**

> ⚠️ **DEMO — реальные деньги не переводятся.** Проект работает только локально. Домен, хостинг,
> реальные платежи (Payme, CLICK и др.), эскроу и публикация в интернете **не подключены**.
> Демо-режим оплаты — это имитация, а не настоящее удержание средств.

## Стек

Next.js 16 (App Router) · React 19 · TypeScript · Tailwind CSS 4 · Zod · Lucide React ·
Supabase (SQL-схема и политики безопасности подготовлены, подключение — на следующем этапе) · Vitest.

Язык интерфейса: русский (основной), узбекский и английский (переключатель в шапке циклически). Валюта: сум (UZS), суммы — **только целые сумы** (в SQL `bigint`; процент комиссии хранится в сотых долях процента, 500 = 5,00 %).

## Запуск на Windows (PowerShell)

Нужен Node.js 20.9+ (проверьте: `node -v`).

```powershell
cd путь\к\uzmarket
npm install
npm run dev
```

Откройте <http://localhost:3000>. Ключи Supabase **не нужны** — приложение работает в демо-режиме
(данные хранятся в `localStorage` браузера, кнопка сброса — в «Кабинет → Настройки»).

Если PowerShell запрещает скрипты: `Set-ExecutionPolicy -Scope Process Bypass`, затем повторите команду.

### Комиссия
Считается и сохраняется **при создании заказа** в хранилище/БД, а не в браузере. Приоритет ставок: продавец → игра → общая. Пример: товар 100 000 сум, ставка 5 % → комиссия 5 000, продавцу 95 000. Применённая комиссия записана в заказ — последующее изменение тарифа старые заказы не меняет.

### Статусы заказа
Ожидает оплаты · Оплачен · В работе · **Товар передан** · Завершён · Открыт спор · Возврат рассматривается · Возвращён · Отменён.
Статусы из ТЗ «Товар передан» и «Ожидает подтверждения покупателя» **объединены в один** (`delivered`): после передачи заказ и есть в ожидании подтверждения покупателя. Это осознанное упрощение.

### Финансовый учёт — только DEMO
Журнал (ledger) только дополняется. Оплата → «ожидает»; завершение заказа → «доступно» (+ комиссия платформы признаётся ровно один раз); возврат/отмена → ожидаемая сумма снимается; заявка на вывод переносит сумму из «доступно» в «в выводе»; «Выплачена» — отметка администратора, **реальный перевод не выполняется**; отклонение возвращает сумму. Продавец не может ни менять статус оплаты, ни отмечать выплату. Минимальный вывод 50 000 сум. Реквизиты, похожие на номер карты/счёта (12+ цифр), отклоняются — вводите только тестовые. **Это не эскроу и не реальные деньги.**

## Безопасность (как устроено)

- Секретов в коде нет; `.env.example` содержит только пустые имена переменных, `.env*` в `.gitignore`.
- Цена, комиссия, роль и статус **не берутся из браузера**: в БД они фиксируются функциями `create_order` / `apply_order_action`; прямые `INSERT/UPDATE` в `orders` и `payments` у клиентов запрещены.
- RLS включён на всех таблицах; на `profiles` у клиента нет права менять `role`, рейтинг, блокировку. Роль администратора назначается **только вручную** через SQL.
- Платёжные события идемпотентны (`unique(provider, event_id)`), событие с неверной подписью отклоняется, журнал аудита неизменяем.
- Деньги — целые сумы (`bigint`), комиссия считается функцией `compute_commission` в БД и фиксируется в заказе; леджер неизменяем, уникальные индексы исключают двойную комиссию/выплату, блокировка по продавцу не даёт балансу уйти в минус при параллельных заявках.
- Первый администратор: только `select public.bootstrap_first_admin('<uuid>')` с service_role / из SQL Editor (и только если админа ещё нет). Через интерфейс администратором стать нельзя.
- В демо-режиме проверки прав выполняются в клиентском хранилище и **не являются защитой** — настоящая защита обеспечивается только политиками БД после подключения Supabase.

## Что нужно до хостинга и реальных платежей

1. Создать проект Supabase, применить миграции `0001`–`0005`, настроить Auth (подтверждение e-mail, защита от перебора), перенести клиентское хранилище на запросы к Supabase.
2. Назначить первого администратора: `select public.bootstrap_first_admin('<uuid>');` (только service_role / SQL Editor).
3. Юридически определить модель удержания и выплаты средств (лицензия платёжной организации или договор с платёжным агрегатором); без этого **не называть сервис эскроу**.
4. Подключить настоящего провайдера (Payme/CLICK/др.) строго по их официальной документации: серверный webhook с проверкой подписи, секреты только в переменных окружения сервера.
5. Подготовить юридические документы с юристом (в репозитории только черновики), проверку возраста/KYC продавцов, модерацию товаров.
6. Домен, HTTPS, хостинг, резервные копии, мониторинг, rate limiting, политика хранения данных.
